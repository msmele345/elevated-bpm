# EB2-01 — Share payloads survive a schema version bump

> Track: v2.0 · Slice 1 of 10
> Depends on: nothing
> Blocks: every later slice (three `ProjectState` version bumps ride on this)
> Branch: `feat/share-payload-migration`
> Resolves review finding: **G6**

## Why this slice goes first

`readSharedBeat` accepts a payload only when its version is *exactly*
`PROJECT_STATE_VERSION`, and anything else returns `unsupported-version`. The
document is at v7 today and this track spends three more versions (v8 for FX,
v9 for the sampler, v10 for the curriculum). Under the current rule, the FX slice
alone silently kills every share link anyone has ever sent.

The link breakage is annoying. The real problem is one slice further out: EB2-08
introduces a **bundle**, which is the same serialization written to a file people
keep. Under an exact-match rule, every bundle a user saves expires the next time
the schema moves. A file format that stops opening is not a file format.

The app already has the machinery to fix this. `migrateProjectState` chains
v0 → v7 and returns null for anything it cannot lift. Share simply is not using
it.

## Scope

### In

- Incoming share payloads are migrated rather than exact-matched.
- `unsupported-version` is reserved for payloads that are genuinely *newer* than
  this build, which is the only version mismatch that cannot be repaired.
- Validation runs on the **migrated** document, so the structural checks in
  `isSharedProject` keep asserting the current shape.

### Out (and where it lands)

- The bundle carrier itself — EB2-08. This slice only makes the pipeline it will
  reuse version-tolerant.
- Any change to what the share payload *contains*. Pads, FX and sampler settings
  join it in their own slices.

## Implementation decisions

- **Migrate, then validate.** The decode path becomes: parse version prefix →
  decompress → JSON parse → `migrateProjectState` → `isSharedProject` on the
  result. A v5 link therefore opens on a v9 build with its beat intact, exactly
  as a v5 IndexedDB document does.
- **The version prefix stays.** It is a cheap pre-decompression guard and it is
  what lets a newer-than-us payload be refused with an honest message instead of
  a confusing structural failure. The check inverts: refuse when
  `version > PROJECT_STATE_VERSION`, migrate everything at or below it.
- **A migration that returns null is malformed, not unsupported.** If
  `migrateProjectState` cannot lift a document it recognizes the version of, the
  payload is damaged. Report it as `malformed` — the user-facing distinction is
  "this link is broken" versus "this link is from a newer Elevated BPM", and a
  failed migration is the former.
- **`projectForSharing` keeps writing the current version.** Outgoing links are
  always current; only the reader is tolerant.
- **Recipient-only fields are re-blanked after migration.** A migrated older
  payload may carry `lessonProgress` or `prefs` that the current
  `isSharedProject` requires to be empty. Blank them as part of preparing the
  incoming document rather than rejecting the link over them — a v5 link
  carrying a stale progress map is a valid beat, not a damaged one.

## Acceptance criteria

- [ ] A share link generated by an older schema version opens on the current
      build with its pattern, tempo and instrument settings intact, via
      `migrateProjectState` rather than a share-specific migration path
- [ ] A payload whose version is newer than this build is refused with the
      `unsupported-version` message and leaves the recipient's project open and
      untouched
- [ ] A payload whose version is known but whose body cannot be migrated or does
      not validate after migration is refused as `malformed`, with the
      recipient's project open and untouched
- [ ] Outgoing links are still written at the current version, and a
      current-version round trip is unchanged
- [ ] A migrated payload carrying non-empty `lessonProgress` or `prefs` opens
      normally, with those fields blanked — an older link does not hand the
      recipient someone else's curriculum progress

## Testing decisions

**Seam: pure model functions** (prior art: `src/model/share.test.ts`).

The whole slice is testable at the model seam, because `readSharedBeat` takes a
URL string and returns a typed result. Extend the existing share suite rather
than starting a new one:

- Build a payload at an older version by hand (the migration suite in
  `src/model/projectState.test.ts` already shows how older documents are
  synthesized) and assert it reads back as `ready` with the expected beat.
- A payload one version *above* current reads back as `unsupported-version`.
- A recognized version whose body is structurally wrong reads back as
  `malformed`.
- Round-trip a current document and assert nothing about the happy path moved.

Do **not** test that `migrateProjectState` was called. Test that an old link
opens — that is the behavior anyone cares about.

## Verification beyond unit tests

Generate a link from the current production build, then apply this change and
open that same link locally. It should load the beat rather than reporting an
incompatible version. This is the one check the unit tests cannot make, because
it uses a payload this codebase did not synthesize.
